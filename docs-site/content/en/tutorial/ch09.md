# Chapter 9: The Permission Control System

AIH's permission system spans every tool call, protecting your machine while preserving flexible automation. This chapter unpacks the core interfaces, interaction flows, and safety guarantees layer by layer.

> **Plain words for newcomers**: think of the AI as an **intern** you hand a permission card:
> - **allow** (green card) — go ahead without asking, e.g. "check whether README exists."
> - **ask** (yellow card) — come ask before acting, e.g. "may I delete this file?"
> - **deny** (red card) — absolutely not, e.g. "never touch the keys in `.env`."
>
> There is also a "**floor**" rule: once a red card is issued, nobody can flip it back to green. That rule is the heart of this chapter.

## The Three-Tier Permission Model

Every ToolDefinition and App Action supports three permission levels: `allow` (auto-approve), `ask` (interactive confirmation), and `deny` (hard block). Permission evaluation is driven by the **ApprovalGate** interface (`core/src/seams/permissions.ts`), whose core method is `request(req): Promise<boolean>`. Built-in implementations include `AutoApprove`, `DenyAll`, `PolicyGate`, and `RulesetGate`.

`RulesetGate` enforces a **priority floor** rule: `deny > ask > allow`. That sounds abstract, but it really means one thing: **a later rule cannot loosen a permission that has already been set**. If a rule raises the floor to `ask`, a subsequent `allow` rule cannot lift it back — this ensures high-security policies are never downgraded by lower-priority rules (see CC#53).

You can read `PolicyGate`'s decision logic like this (simplified):

```ts
async request(req): Promise<boolean> {
  for (const rule of this.rules) {
    if (rule.match(req)) {
      if (rule.action === "allow") return true;  // green card → allow
      if (rule.action === "deny")  return false; // red card → deny
      break;                                     // yellow card → ask below
    }
  }
  // falls through to ask: ask the user (no later allow can lift it back)
  return this.fallback.request(req);
}
```

> **An analogy to keep you unconfused**: the priority floor is like a safety lock you can only ever tighten, never loosen. Once a `deny` locks in, no later `allow` can open it.

## Rules and Scoping

Each permission rule is a triple: `PermissionRule {tool, pattern, action}`. Matching uses `matchPattern` (glob converted to regex; `**` matches any path segment, `*` matches within one segment). Scoping is computed by `deriveScope` — it takes the parent directory of the target path and appends `/**`. The path reader `targetOf` accepts multiple key names: `path`, `file`, `dir`, `directory`, `target`.

This design lets you declare precise boundaries: allow writes only under `/app/src/**`, or deny reads of `.env` files specifically. Scopes inherit automatically, eliminating redundant declarations.

## SessionGate: Interactive Approval

`SessionGate` (`cli/src/gate.ts`) handles permission requests that need human input. In a TTY it offers a three-way choice: `[y]es` (allow this time), `[n]o` (deny), `[a]lways` (allow for the rest of the session).

Read-only commands are auto-approved via `isReadonlyCommand` and the `read` kind (**"just looking" = green by default**). For WRITE shell commands, SessionGate offers a run-or-copy mode: you can execute directly, copy to the clipboard (never executes), or cancel. Notably, injected input (`serve`/`attach`) can never approve an `ask` — this is a hard safety boundary (CC#60); see [Ch.16](ch16) on the injected-session security constraints.

## Project Trust and Doom-Loop Guard

**Project trust** (`cli/src/project-trust.ts`) manages trust on a per-directory basis, stored in `trust.json` under the user's global config directory. A project cannot trust itself. Trust is controlled via `--trust` / `--no-trust` flags; non-interactive mode defaults to deny (fail closed). Moving a directory triggers a re-prompt.

The **doom-loop guard** lives in the tool-registry: if the same permission request is asked `>=3` times in a row, it escalates to deny; at `>=6` times, it becomes a permanent deny. This prevents tools from entering an infinite retry loop of approval prompts — **if the AI keeps trying to do the same thing that needs confirmation, the system says "no" for you and stops**.

## Summary

AIH's permission system is a defense-in-depth architecture: the core layer provides policy interfaces, SessionGate manages interactive UX, project trust secures directory-level safety, and the doom-loop guard preserves system stability. Understanding these mechanisms is essential for safe AIH usage and for building custom permission policies. For more CLI-level details, see [command reference](../commands).
