# Plugin & Extension System

AIH's extensibility is built on a unified extension architecture. Plugins can register new tools and commands, or intercept and modify existing tool I/O via hooks—but all hooks run *after* redaction and audit, ensuring the security boundary is never bypassed.

## Loading Flow

Plugin loading is driven by `loadExtensions(...)` in `cli/src/extensions.ts`. At startup, AIH scans and loads plugins in this order:

1. Project-level plugins (`.aih/extensions/` directory)
2. User-level plugins (XDG data directory)
3. Built-in plugins

Project-level plugins are only loaded when the **project is trusted** (project trust gate). If the project hasn't been granted trust, its extension directory is completely ignored. This prevents malicious repositories from injecting code through plugins.

## Tool & Command Registration

Plugins interact with AIH through three core APIs:

- **`registerTool`** — Registers a new tool, making it available in the model's tool list. If the registered tool shares a name with a built-in tool, **tool shadowing** occurs: the extension's tool replaces the built-in one but inherits its basic rendering behavior.
- **`registerCommand`** — Registers a new CLI command, extending the command-line interface.
- **`on`** — Registers event listeners that respond to lifecycle events.

Together these three form the complete interface between extensions and the AIH core.

## Hook Waterfall

Hooks are the most powerful extension capability. Built via `hookSet()` and registered through `registry.addHooks(hookSet)`, they inject custom logic before and after tool execution.

Critical design: **extension hooks run last in the waterfall**. This means they see results that have already been redacted and audited, and any modifications they make are themselves logged. The security layer always executes before extensions.

Supported hook events:

| Event | When it fires |
|---|---|
| `tool:before` | Before a tool call executes |
| `tool:after` | After a tool call completes |
| `turn:end` | When a conversation turn ends |

The `onEvent` API lets you listen for these events to implement logging enhancements, result filtering, automatic retries, and other advanced patterns.

## AskError: Forced Human Confirmation

Extensions can throw an `AskError` exception. This is not a silent veto—it triggers a **human confirmation floor** (CC#53), requiring explicit user approval before the system proceeds. This is more transparent than a simple rejection and is intended for cases where a plugin needs human review before safe execution.

For example, a deployment plugin can throw `AskError` before executing `apply_patch`, requiring the user to confirm the changes.

## Disabling & Safety

When extension capabilities aren't needed, pass `--no-extensions` to completely disable all plugin loading. This is especially useful in CI/CD environments or security-sensitive contexts.

Additionally, all extension hook inputs and outputs are recorded in the audit log, ensuring every modification is traceable. Combined with hooks running last in the waterfall, AIH maintains a reliable security boundary while offering open extensibility.
