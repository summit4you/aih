# IDE & Headless Access

AIH doesn't just run as an interactive terminal—it supports headless services, the MCP protocol, and SDK embedding for connecting to external tools and IDEs. This chapter covers how these access patterns work and when to use each.

## Headless Service: serve & attach

`cli/src/serve.ts` provides AIH's headless service mode. Start with `aih serve`, connect with `aih attach`, and you get fully automated AI interaction.

The service exposes these HTTP routes:

| Route | Function |
|---|---|
| `/health` | Health check |
| `/events` | SSE event stream |
| `/message` | Send a message |
| `/tools` | List available tools |

The SSE (Server-Sent Events) stream provides real-time event pushing, suitable for building web interfaces or monitoring dashboards.

## Security Constraints for Injected Turns

Turns injected via `POST /message` or steering have their `inputSource` set to `"injected"`. This is a critical security boundary: **injected turns can never approve a permission ask** (CC#60).

Permission confirmations must originate from a local TTY terminal. This prevents remote attackers from bypassing human confirmation by injecting messages—an essential component of AIH's security model.

## MCP as IDE Bridge

MCP (Model Context Protocol) lets AIH tools be consumed by any MCP client. Through the `mcp-server` component, AIH tools can be mounted into:

- **opencode / codex / claude** and other AI coding assistants
- **VS Code** and other MCP-compatible IDEs
- Any client supporting the MCP protocol

When multiple MCP servers provide tools with the same name, **cross-server name collisions** occur. AIH resolves this automatically by renaming to `<server>_<tool>` format, ensuring every tool has a unique identifier.

## Three Integration Shapes

AIH offers three primary integration approaches depending on your use case. The three shapes share the same core capabilities—only the access layer differs—ensuring consistent functionality and security guarantees regardless of which approach you choose.
