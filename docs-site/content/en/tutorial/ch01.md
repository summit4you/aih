# From Coding Assistants to the AIH Positioning

## Three Generations of Programming Assistants

The first generation of coding assistants offered **inline completion** — suggestions popped up at the cursor, accepted with Tab. The second added **conversational Q&A** — describe a need, get a code snippet back. We are now in the third generation: **agentic coding** — models that own tools (read files, run commands, edit code), autonomously plan multi-step execution, and work like a permissioned developer.

AIH (App Intelligence Harness) is born at this inflection point. As its README states:

> A universal framework for making ordinary applications AI-assisted.

AIH is not merely a "coding assistant" but an **app intelligence harness**. The coding scenario is just its first and most mature use case.

## AIH's Lineage: deepseek-harness + opencode

AIH merges core designs from two upstream projects:

| Source | Key contribution | Landing |
|---|---|---|
| deepseek-harness | append-only Session Log, guard-pipeline tools, Agent Loop, replaceable Seams | `core/` (L1 kernel) |
| opencode | build/plan dual modes, permission model, SKILL.md progressive disclosure, TUI | `cli/` (CLI + TUI), skill loading |

The **append-only session log** means every event (tool call, LLM response, user input) is only appended, never modified — crash-recoverable and audit-replayable. The **guard-pipeline ToolRegistry** passes every tool execution through a permission check (allow / ask / deny) and hook chain (redaction, timing, audit) before it runs. **Seams** define replaceable interfaces for the LLM adapter, sandbox backend, approval gate, and skill loader — swap a model provider or approval strategy without touching the kernel.

## Three Integration Shapes

AIH's core value proposition is "bring AI to your app without changing business code." It offers three shapes:

- **MCP Plugin** (recommended starting point): Expose your app's tools via Model Context Protocol to any MCP client — opencode, codex, Claude Code, etc. Zero intrusion — the app side only needs to implement the `AppAdapter` interface.
- **CLI**: The `aih` command provides an interactive terminal (opencode-style TUI), one-shot Q&A (`aih run`), and script pipelines.
- **Embedded SDK**: `import` `@aih/core` directly, register tools into `AgentLoop`, and build custom copilots.

All three share the same **L0 contract**: `AppAdapter` = `descriptor` (app description) + `context(query)` (read state) + `actions` (write operations with permissions).

## AppAdapter: Where Everything Begins

Integrating with AIH requires implementing three primitives:

| Primitive | Type | Permission | Purpose |
|---|---|---|---|
| **Context** | read | `allow` (executed directly) | Query app state |
| **Action** | write | `allow` / `ask` / `deny` | Execute business operations |
| **Event** | stream | optional | Push state-change events |

Take the built-in todo-app example (`mcp-server/src/app-adapter.ts`): `list_todos` is an `allow`-level Action, while `toggle_todo` and `remove_todo` are `ask`-level — requiring user confirmation before execution. This three-tier permission model runs through the entire AIH architecture.

## Why a "Universal Framework"

AIH deliberately **avoids coupling to any business logic**. The kernel (`core/`) contains no application-specific code; all business tools are injected via `AppAdapter`. This means the same AIH kernel can power a code editor, database management tool, CI pipeline, or mobile debugging panel — as long as they implement the L0 contract. This design makes "attaching intelligence to any application" possible, not just "building a better Copilot for programmers."
