# The Tool System

AIH's tool system is the bridge between the agent and the outside world. All tools are registered, looked up, and invoked through the `ToolRegistry`.

> **Plain words for newcomers**: tools are the AI's **hands** — it can't read files or run commands on its own; it relies on calling tools. `ToolRegistry` is like a **registry of every tool**. When the AI wants to do something, it looks a tool up by name — and before that call is truly let through, it has to pass **five security checkpoints**. This chapter is about how that "registry + checkpoints" is built.

## ToolRegistry and ToolDefinition

`ToolRegistry` (`core/src/tool-registry.ts`) provides four core methods: `register`, `get`, `schemas`, and `invoke`. Each tool is a `ToolDefinition` object — essentially a "tool user manual":

```ts
interface ToolDefinition {
  name: string;                                  // tool name, how the AI refers to it
  description: string;                           // tells the AI "what this tool does"
  kind: "read" | "write";                        // read or write (read = parallel, write = serial)
  permission: "allow" | "ask" | "deny"           // three permission tiers (static or a function)
             | ((args) => ...);
  parameters: ToolSchema["parameters"];          // parameter schema, so the AI knows what to pass
  execute(args, ctx): Promise<unknown>;          // the function that actually does the work
}
```

`register`'s implementation is straightforward — it **only registers, and forbids duplicates**:

```ts
register(def: ToolDefinition): this {
  if (this.#tools.has(def.name)) throw new Error(`tool already registered: ${def.name}`);
  this.#tools.set(def.name, def);   // add to the registry
  return this;
}
```

Calling `schemas()` returns an array of `ToolSchema` objects (name, description, parameters) that the model uses to decide "which tool to call next."

## The Guard Pipeline: Five Checkpoints per Invocation

Every tool invocation passes through five guard stages in `invoke()`. Why all the barriers? Because the AI is "external input" — every action it wants to take should be scrutinized under **least-privilege**.

Against the source, the core of `invoke` reads like this (simplified but faithful):

```ts
async invoke(name, input) {
  const def = this.#tools.get(name);
  if (!def) return { ok: false, error: this.#planHint
      ? `unknown tool: ${name} — not available in read-only (plan) mode`
      : `unknown tool: ${name}` };                 // 0) not in registry → fail immediately

  const permission = resolve(def.permission);      // 1) resolve permission
  if (permission === "denied")
    return { ok: false, permission: "denied" };     //    denied → reject immediately

  const repeats = this.#countRepeats(name, input);  // 2) doom-loop counter
  if (repeats >= DOOM_LOOP_DENY_AT)                 //    >=6 times → hard deny
    return { ok: false, permission: "denied" };     //    >=3 times → ask (DOOM_LOOP_ASK_AT)

  await hooks.before(...);                          // 3) before hooks: redact/time/audit
  const result = await def.execute(input, ctx);     // 4) actually execute
  await hooks.after(...);                           // 5) after hooks: rewrite/audit
  return result;
}
```

The five stages:

1. **Permission resolution**: resolves `def.permission` (static string or function) to allow/deny. Denial returns a denied result immediately.
2. **Doom-loop detection**: when identical calls repeat—at `DOOM_LOOP_ASK_AT = 3` it asks the user for confirmation, at `DOOM_LOOP_DENY_AT = 6` it hard-denies. This stops the AI from retrying the same step endlessly.
3. **Before hooks**: perform redaction, timing, and audit; if `AskError` is raised, human confirmation is forced (CC#53 — nobody can bypass the "ask a human" floor).
4. **Execute**: runs the tool's actual logic via `def.execute`.
5. **After hooks**: result rewriting and audit logging.

## App Tools and Built-in General Tools

AIH tools come from two sources:

- **App tools**: provided by `AppAdapter` actions (see [Ch.8](ch08)).
- **Built-in general tools** (`cli/src/dev-tools.ts` + `general-tools.ts`): `list_dir`, `read_file`, `write_file`, `run_cmd`, `edit`, `glob`, `grep`, `webfetch`, `websearch`, `task`, `best_of_n`, `question`, `remember`, `load_skill`, `todo`.

When an app tool and a built-in tool share the same name, the **app tool wins**.

## Parallel Read-Only Execution

To improve efficiency, AIH supports parallel read-only calls (F#29): consecutive read-only tool invocations run concurrently, capped at `AIH_TOOL_CONCURRENCY` (default 4). Write operations always execute serially. All results are returned in the original call order, implemented via `mapConcurrent` in `agent-loop.ts`.

> **Why can reads run in parallel but not writes?** A read just "looks at" something — looking at several places at once is harmless. A write "changes" something — concurrent changes race and trample each other. So the system hands reads a "you may all go at once" pass, and writes a "line up one at a time" baton.
