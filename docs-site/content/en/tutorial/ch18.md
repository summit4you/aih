# Chapter 18 Design Philosophy & Best Practices

This chapter distills the design philosophy behind AIH and provides actionable guidance for real-world projects.

## 18.1 Core Design Principles

AIH is built on three non-negotiable principles:

**Append-only**: Sessions and audit logs are never mutated in place. Rollback = fork from a prefix. This makes history traceable and reproducible.

**Seam-first**: Every pluggable point is an interface — LLM, sandbox, approval gate, skill loader. New capabilities are added by implementing an interface, not by modifying the kernel.

**General kernel + injected app tools**: The AIH kernel carries no application logic. Apps inject tools through `AppAdapter` into a `ToolRegistry`, which is handed to `AgentLoop` (see [Ch.17](ch17) for a concrete walkthrough).

## 18.2 Trust Model

AIH's trust model is defined by explicit boundaries (see [APP.md](../adapter)):

- **Local single operator**: the trust boundary is the host OS user.
- **Three-state permissions**: `allow` (no confirmation), `ask` (user confirmation required), `deny` (hard block). Write operations default to `ask`.
- **Credential redaction & owner isolation**: sensitive credentials are redacted in logs; context between different apps is isolated.
- **Sandbox seam**: the execution environment can be isolated through the sandbox interface.
- **Deny red lines**: `deny` cannot be overridden by the model.

**Not in the threat model**: prompt-injection-only attacks. For true isolation, use a separate agent/host (separate OS user or container), not prompt- or session-level isolation.

## 18.3 Governance & Evolution Rules

AIH follows layered governance:

- **OC#2 core per-call tax** vs **skill/extension layer**: when a feature is wired in ≥2 places, extract a seam into core/SDK; one-off domain needs stay in skill/extension.
- **Quality regression gate**: `aih quality --mock` uses an FB#4 buffbench-style task suite + baseline; live runs gate on zero regressions.
- **Coverage scorecard**: `aih coverage --profile release` (OC#6), coverage-ID + evidence mode; the registry is derived from smoke groupings and never drifts.
- **eval hand-off gate**: `npm run eval`, detailed in [Ch.17](ch17).

## 18.4 Best Practices Checklist

| Practice | Notes |
|---|---|
| **Plan-then-build (Tab)** | For risky changes, use the plan mode — the AI outputs a proposal before executing |
| **Keep writes behind ask** | Unless fully controlled, do not set write actions to `allow` |
| **Prefer parallel read-only tools** | Multiple read tools can run in parallel, significantly cutting latency |
| **Keep sessions append-only** | Enables replay and debugging; never modify historical entries |
| **Set a /goal condition** | For long autonomous tasks, define a termination condition to prevent infinite loops |
| **Use skills for domain knowledge** | Put domain knowledge in skills, not in the system prompt |
| **Keep flat config** | Top-level `model` / `baseUrl` is the recommended shape; legacy shapes remain legal — migration stamps `CONFIG_SCHEMA_VERSION` and never touches flat fields |

## 18.5 Summary and Outlook

AIH's philosophy can be summed up: smallest kernel, strongest seams, clearest trust boundaries — an evolving foundation for AI agents. With the [quick start](../quickstart) for onboarding, [configuration](../config) for details, and [Ch.17](ch17) for hands-on practice, you have everything needed to integrate any application into AIH. The skill system and community ecosystem are the next frontiers to explore.
