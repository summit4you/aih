# Overall Architecture Design

## The Four Layers at a Glance

AIH's architecture consists of four layers plus one cross-cutting concern, each with distinct responsibilities:

<figure>
<img src="assets/tutorial/arch-overview.svg" alt="AIH four-layer architecture diagram" />
<figcaption>Figure: AIH four-layer architecture — L0 Adapter → L1 Kernel → L2 Protocol → L3 Skills, with cross-cutting permissions, audit, and gates</figcaption>
</figure>

```
L3 Skills     skills/           On-demand domain knowledge, self-evolving via skill-creator
L2 Protocol   APP.md · harness.yml · scripts · tasks · docs/decisions.md
L1 Kernel     core/             SessionLog · ToolRegistry (guard pipeline) · AgentLoop (turn/step) · Seams (LLM/permissions)
L0 Adapter    mcp-server/       AppAdapter: Context (read) / Action (write, with permissions) / Event (stream)
Cross-cutting  allow/ask/deny permissions · audit log · eval handoff gate
```

- **L0 Adapter Layer**: One app = one `AppAdapter` (`descriptor` + `context(query)` + `actions`). This is the **single** integration surface. All three shapes (MCP / CLI / SDK) share the same L0 contract.
- **L1 Kernel Layer** (`core/`): SessionLog, ToolRegistry, AgentLoop, Seams — the kernel contains zero business logic; tools are injected by L0.
- **L2 Protocol Layer**: `APP.md` (app contract), `harness.yml` (declarative config), `scripts/` (doctor/check/eval gates), `docs/decisions.md` (decision records).
- **L3 Skills Layer**: SKILL.md three-level loading (project > user > builtin) + BM25 relevance-based auto-suggestions + external registry installation.
- **Cross-cutting**: Three-tier permissions (allow / ask / deny) with pattern/path scoping; audit log appends each tool call to `.aih/tool-audit.jsonl`; `npm run eval` as the handoff gate.

## Core Data Flow

A single user interaction follows this path:

```
User input
  → AgentLoop turn (L1)
    → ToolRegistry receives tool call request
      → Permission guard: allow / ask(deny) / deny
        → Hook chain (redact / timing / audit)
          → AppAdapter.action() (L0, executes the actual business operation)
            → AppAdapter.event() (optional, pushes state-change events)
              → SessionLog.append() (writes to append-only JSONL)
                → Result returns to AgentLoop → next step or output to user
```

Key design principles:

- **append-only**: Session and audit logs are append-only — crash-recoverable, rollback = prefix fork.
- **Decoupled judgment from execution**: The Goal judge (independent LLM call verifying goal completion) and best_of_n judge are independent of the executing agent.
- **Parallel reads**: Consecutive read-only tool calls within a single step execute concurrently (capped at `AIH_TOOL_CONCURRENCY`, default 4); writes stay serial.

## The Seam Replaceability Mechanism

Seams are the most important design pattern in AIH's architecture. `core/seams/` defines the following replaceable interfaces:

| Seam | Purpose | Replacement scenario |
|---|---|---|
| **LLM Adapter** | Abstracts LLM calls behind a unified interface | Switch between DeepSeek / OpenAI / local models |
| **Sandbox Backend** | Isolation environment for tool execution | local → bwrap → remote (D#12) |
| **Approval Gate** | Routes allow/ask/deny decisions | Custom approval workflows |
| **Skill Loader** | Discovers and loads SKILL.md files | Custom skill discovery strategies |

The core value of Seams: **pluggable but not locked in**. Replace the LLM provider without changing a single line of kernel code. Switch sandbox strategies to fit different deployment environments.

## Layered Configuration

AIH's configuration stacks in layers, from application-level down to project-level and user-level overrides:

| Config source | Location | Purpose |
|---|---|---|
| `APP.md` | Project root | App intelligence agent contract — single source of truth; defines capability boundaries, integration primitives, change rules |
| `harness.yml` | Project root | Declarative harness config (LLM parameters, model selection, etc.) |
| `aih.json` | Project root | Runtime config (provider, model, API key, etc.) |
| Project trust gate | `cli/src/project-trust.ts` | First-time trust confirmation when opening a project |
| Environment variables | `AIH_API_KEY` / `AIH_MODEL` / `AIH_BASE_URL` | Override corresponding config file entries |

Config loading is unified by `cli/src/config.ts` with precedence: env vars > CLI flags > `aih.json` > `harness.yml` > `APP.md` defaults.

## Key Design Decisions Summary

| Principle | Meaning |
|---|---|
| Generic kernel + app tools | Kernel has zero business coupling; tools injected by AppAdapter |
| append-only | Session/audit logs only append; rollback = prefix fork; crash-recoverable |
| Seam-first | LLM/sandbox/approval/skills are all seams — pluggable, never locked |
| Decoupled judgment from execution | Goal judge and best_of_n judge are independent of the executing agent |

With this four-layer architecture understood, you are ready to [build your own AppAdapter](ch04) — starting from the simplest L0 adapter and progressively integrating the skills and protocol layers.
