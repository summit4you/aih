# Ch.19 · Case study: HemaGuide clinical decision support

The previous chapters dissect AIH itself. This chapter flips the perspective: a **domain
application** — HemaGuide, a clinical decision-support system for hematologic malignancies —
riding on AIH's existing primitives (extension / workflow / skill / shared lib) **without a
single line of core changed**. It is the most complete instance of "generic kernel + injected
domain logic" ([Ch.18](ch18)).

> **One line for newcomers**: when a hematologist faces a relapsed case or an NGS report,
> they have to assemble guidelines, prior cases, and molecular evidence into a
> "tumor-board style resolution." HemaGuide lets the LLM do what it's good at — extraction,
> routing, synthesis — while the **numeric scoring** that must never be free-form is done by
> code.

> **Safety boundary (throughout)**: every case and every molecular evidence entry here is
> **synthetic, de-identified** stand-in data. The implementation and docs are marked
> **RESEARCH USE ONLY** — not for patient care or real clinical use. Any "resolution" must be
> independently verified by qualified medical professionals before it is considered.

## 19.1 Background: what the paper tries to solve

HemaGuide (*Clinical Decision Support in Hematological Malignancies Using a Case-Grounded AI
Agent*) targets decision support in hematologic malignancies (AML, DLBCL, multiple myeloma,
…). Its core thesis:

**Numeric / structured reasoning must not be left to a free-form LLM.** Variant scoring,
threshold decisions, and mutual-exclusion rules must live in auditable code; the LLM only
does extraction, routing, and synthesis.

The paper splits decisions into three modes:

| Mode | When | Evidence source |
|---|---|---|
| **GUIDELINE** | Case follows a disease flowchart (first-line, standard therapy) | Guideline flowchart data |
| **ADVANCED** | Case goes beyond guidelines (rare markers, prior failures, needs precedent) | Prior case memory (vector retrieval) |
| **MOLECULAR** | Molecular tumor board / NGS variant interpretation | Molecular evidence + **deterministic scoring model** |

Behind MOLECULAR is a 12-criteria oncogenicity model (Horak et al. 2022 / ClinGen-CGC-VICC
lineage): population frequency, hotspots, variant type, domains, functional evidence, and
computational prediction. Positive and negative points are summed and mapped to five tiers —
`Oncogenic ≥10` · `Likely Oncogenic 6–9` · `VUS 0–5` · `Likely Benign −6~−1` · `Benign ≤−7` —
with mutual-exclusion rules (e.g. once the strong oncogenic criterion OS3 is met, the weaker
OM1 is not stacked on top).

## 19.2 Mapping the paper onto AIH primitives

The reproduction in this repo (`examples/hemaguide/`) maps every part of the paper onto AIH
primitives, **with zero core changes**:

| HemaGuide (reference) | This implementation (AIH primitives) | Why |
|---|---|---|
| `src/mol/*` 8 evidence layers → scoring tool | **`lib/scorer.mjs`** (deterministic 12-criteria scoring) | The paper's safety floor: scoring is **code**, not LLM. Pure functions, offline-testable, assertable. |
| `src/vectordb.py` (vector DB over prior cases) | **`lib/retriever.mjs`** (BM25 retrieval, CJK/latin-aware) | Same design intent (retrieve similar cases, filter by entity, rank by fragment overlap) but **zero external services** — runs offline on commodity hardware. |
| `src/decision.py` three decision modes | **three extension tools** + **workflow route phase** | LLM routes to a mode (the part the paper leaves to the model); code executes the mode (the part the paper insists must not be free-form). |
| `data/onkopedia.json` (guideline flowcharts) | **`data/flowcharts.json`** | Evidence source for GUIDELINE mode. |
| Gene classification table + 8 upstream APIs | **`data/molecular-evidence.json`** (local curated table) | Stands in for the 8 upstream APIs (gnomAD / cancerhotspots / CIViC / OncoKB / …) so scoring runs offline. |
| `src/extraction.py` (8-section case extraction) | **workflow `extract` phase** | LLM structures free-text cases into 8 sections (age/ECOG/diagnosis/…/molecular). |
| Full pipeline (extract→route→evidence→synthesize) | **`.aih/workflows/hemaguide.mjs`** (4 phases, each with an `expect` substring gate) | Machine-decidable, fail-fast: a wrong or missing answer does not propagate. |

## 19.3 The deterministic scoring core

`lib/scorer.mjs` is a faithful JS port of the paper's `src/mol/*`. The 12-criteria point table:

| Dimension | Criteria | Points |
|---|---|---|
| Population frequency | SBVS1 (MAF>5%) / SBS1 (MAF>1%) | −8 / −4 |
| Population frequency | OP4 (MAF<0.01% or absent) | +1 |
| Hotspots | OS3 / OM3 / OP3 | +4 / +2 / +1 |
| Variant type | OVS1 (null in a tumor suppressor) / OM2 (in-frame indel in a cancer gene) | +8 / +2 |
| Domain | OM1 (critical functional domain) | +2 |
| Functional evidence | OS2 (in vitro / in vivo studies) | +4 |
| Computational prediction | OP1 / SBP1 | +1 / −1 |

Mutual-exclusion rules prevent double-counting within a dimension (e.g. once OS3 is met,
OM1 is not stacked). Input is a variant list; output is **per-criterion hit detail + total +
five-tier classification** — and because every step is a pure function, it can be
`assert`ed: `TP53 p.Arg273His → 10 → Oncogenic`, `NPM1 mutation (no OVS1) → 7 → Likely
Oncogenic` are exactly the kind of assertions baked into the verification scripts.

## 19.4 Three entry points: CLI / interactive tools / deterministic pipeline

One shared `lib/`, three entry points — this is "repeated need → seam" ([Ch.18](ch18)) in
action:

```bash
# ① Direct CLI: deterministic core, no LLM, runs offline
node examples/hemaguide/bin/hemaguide.mjs score '{"variants":[{"gene":"TP53","aa_change":"p.Arg273His"}]}'
node examples/hemaguide/bin/hemaguide.mjs retrieve --query "relapsed AML TP53" --entity AML
node examples/hemaguide/bin/hemaguide.mjs flowchart --entity AML
```

```text
# ② Interactive: the extension registers the three modes as tools (auto-loaded by aih run / chat / tui)
> hemaguide_score { "variants": [...] }
> hemaguide_retrieve { "query": "relapsed AML TP53 complex karyotype" }
> hemaguide_flowchart { "entity": "AML" }
```

```bash
# ③ Deterministic pipeline: 4-phase workflow, runs end-to-end on a local model
AIH_BASE_URL=<your OpenAI-compatible endpoint> AIH_MODEL=<model> AIH_API_KEY=<key> \
node cli/dist/index.js workflow run hemaguide --dev --yes
```

> **Key architectural constraint**: the `aih workflow run` path does **not** load
> extensions, but it does expose `run_cmd`. So the workflow's deterministic evidence steps go
> through the **shared CLI** (`bin/hemaguide.mjs`) via `run_cmd` — the **same `lib/` code**
> the extension and the direct CLI use, no copy-paste; interactive tools go through the
> extension (only `aih run`/`chat` load extensions).

## 19.5 The PHI safety gate: "ask a human" as code

The extension installs a PHI (protected health information) gate on the `tool:before` hook:
any `hemaguide_*` tool call whose arguments carry a **direct patient identifier** (SSN /
patient-id / DOB / email, …) is blocked outright, with a demand to de-identify first. It is
not a prompt-level "please be careful" — it is a hard gate that cancels the call before it
runs. Same shape as "the safety layer always precedes the extension" from [Ch.13](ch13),
except here the domain side defines the safety layer itself.

## 19.7 Takeaways

- **Domain logic stays out of the core**: all of HemaGuide's scoring / retrieval / data lives
  in `examples/` and `.aih/extensions|workflows`; AIH core is untouched — that is "generic
  kernel + injected app tools."
- **Numeric reasoning belongs to code, orchestration to the LLM**: scoring is pure
  functions (assertable, offline-reproducible); the LLM only extracts / routes / synthesizes,
  and the synthesis must cite the deterministic classification and points.
- **One `lib/`, three entry points**: CLI, extension tools, and the workflow (via `run_cmd`)
  reuse the same code.
- **Safety is explicit**: RESEARCH USE ONLY runs through the data and the docs; the PHI gate
  is a pre-call cancellation, not a prompt convention.
