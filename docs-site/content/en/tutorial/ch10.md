# Chapter 10: Snapshots and the File System

File operations are the most frequent AI interactions. AIH strikes a careful balance between "getting things done" and "not breaking things" — through its snapshot system, sandbox isolation, and fine-grained file tool permissions.

> **Plain words for newcomers**: think of the AI as an assistant with a **"undo button + isolation gloves"**. It can rewind if it makes changes (snapshots), wears the gloves when handling sensitive files (sandbox), and has to ask you before touching your files (permissions). Together these make it safe to let the AI work.

## Session Snapshot Mechanism

AIH manages session state with an **append-only log** model. Each operation produces a `SessionEvent`, forming a replayable timeline. Core operations include:

- **Checkpoint**: Save a state snapshot (`cli/src/sessions.ts`)
- **Restore**: Roll back to the most recent checkpoint
- **Fork**: Create a branch from the current state, forming a session tree
- **Recovery** (`recovery.ts`): Scan and repair truncated log tails

The `coverageDigest` mechanism ensures projection data is verifiable — snapshots aren't just state copies but audit foundations. You can review exactly what the AI changed at any point. For the full implementation of the append-only stream and fork/rollback (with a diagram), see [Ch.4 "The Session System"](ch04).

> **One line to remember**: a snapshot isn't "copying a file aside" — it's "keeping the event prefix that lets state be replayed." Rollback = re-forking from the save-point.

## Sandbox Backends

Write operations can be isolated via the **SandboxBackend** (`cli/src/sandbox.ts`). Three backends are supported:

| Backend | Description |
|---------|-------------|
| `local` | Default; executes directly on the host |
| `bwrap` | Isolated via Bubblewrap sandbox |
| `remote` | Executes in a remote sandbox (default host from `AIH_REMOTE_HOST`) |

The **resolution priority** for the sandbox backend (`cli/src/sandbox.ts`) is:

1. The `sandbox` argument on each `run_cmd` call
2. The `AIH_SANDBOX` environment variable (`local` / `bwrap` / `remote` / a custom registered name)
3. The default `local`

> **What is a sandbox?** It's the "execution room" `run_cmd` runs in: `bwrap` makes the working directory read-only and only leaves `/tmp` writable, running the command with least privilege; `remote` sends the command to a remote host over ssh. Either way, **read-only operations stay locally safe** — just looking, not touching, needs no isolation.

## The File Toolset

AIH provides a carefully designed set of file operation tools:

- `read_file`: Read a text file, 64KB cap, supports line offsets
- `write_file`: Create or overwrite a file
- `edit`: Exact string replacement (use `replace_all` when ambiguous)
- `list_dir`: List directory contents
- `glob`: Find files by pattern
- `grep`: Regex search file contents

The permission rule is straightforward: **all reads are auto-allowed; all writes require confirmation**. This is the principle of least privilege in action — the AI can freely inspect, but modifications need your consent. This "read = green card, write = ask" decision mechanism is exactly how the three permission tiers in [Ch.9 "The Permission Control System"](ch09) apply to the file tools.

## Environment Filtering and Credential Protection

`cli/src/env-policy.ts` enforces strict environment variable filtering when spawning child processes. The following types of variables are stripped:

- Variables containing `KEY`, `TOKEN`, `SECRET`, `PASSWORD`
- All `AIH_*API*` core credentials

Credentials follow owner isolation — keys are only sent to the owner endpoint. This ensures your sensitive information never leaks even when AI tools call external services.

## Summary

The file system is AIH's most powerful yet most dangerous capability. Snapshots provide an undo mechanism, sandboxes provide isolation walls, the permission model provides approval gates, and environment filtering provides a data firewall. Layered defenses let you confidently let the AI work. For the tool-execution guard pipeline, see [Ch.5 "The Tool System"](ch05).
