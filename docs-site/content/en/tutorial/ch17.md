# Chapter 17 Hands-on: Integrate an App End-to-End

This chapter uses the built-in Todo app as a reference implementation. We walk through every step from adapter authoring to quality verification. Review the [adapter spec](../adapter) before starting.

## 17.1 The Real TodoAppAdapter Interface

AIH's core abstraction is `AppAdapter`, defined in `mcp-server/src/app-adapter.ts`. Every adapter exposes a `descriptor` (metadata) and two mounting surfaces: `context(query)` and `actions`:

```ts
// The interface every adapter must implement
interface AppAdapter {
  readonly descriptor: {
    name: string;
    version: string;
    description: string;
    contextQueries: string[];
    actions: Record<string, AppActionDef>;
  };
  context(query: string): Promise<unknown>;
  actions: Record<string, AppActionDef>;
}

// Structure of each action
interface AppActionDef {
  description: string;
  kind: "read" | "write";
  permission: "allow" | "ask" | "deny";
  parameters: ZodSchema;        // validated with zod
  run: (args: Record<string, unknown>) => Promise<unknown>;
}
```

The Todo app registers four actions: `list_todos` (read/allow), `add_todo` (write/allow), `toggle_todo` (write/ask), `remove_todo` (write/ask). It also exposes four context queries: `all`, `open`, `done`, `stats`.

## 17.2 Writing a Custom Action

Below is a read-only action that counts completed todos, added to the existing TodoAppAdapter:

```ts
import { z } from "zod";

const countDoneAction = {
  description: "Count completed todos",
  kind: "read" as const,
  permission: "allow" as const,
  parameters: z.object({}),
  run: async () => {
    const todos = await context("done");
    return { count: todos.length };
  },
};
```

Key points: `kind:"read"` + `permission:"allow"` lets the model call it without confirmation; `kind:"write"` actions default to `ask`, prompting the user. Parameters use a zod object schema so the model always generates valid input.

## 17.3 CLI Wiring and Running

The AIH CLI mounts each adapter action as a top-level tool command: `list_todos`, `add_todo`, `toggle_todo`, `remove_todo`. Write operations prompt `[y/N]` confirmation in TTY mode; non-TTY mode requires `--yes` to skip.

Three ways to launch:
- **Interactive TUI**: run `aih` for a live terminal session.
- **Offline mode**: `aih run "<prompt>" --mock` — no real model needed.
- **Real model**: set `AIH_BASE_URL`, `AIH_MODEL`, `AIH_API_KEY`, then `aih run "<prompt>"`.

## 17.4 Embedding via @aih/core

To embed AIH in your own process, use the `ToolRegistry` and `AgentLoop` from `@aih/core`:

```ts
import { ToolRegistry, AgentLoop } from "@aih/core";

const registry = new ToolRegistry();
registry.register({
  name: "list_todos",
  description: "List all todos",
  kind: "read",
  permission: "allow",
  run: async () => { /* ... */ },
});

const loop = new AgentLoop({ tools: registry, /* model config */ });
await loop.run("List all incomplete tasks");
```

This is the "general kernel + injected app tools" pattern described in [Ch.16](ch16).

## 17.5 Quality Gate: honesty gate

After integration, three checks must pass:

| Command | Purpose | Scope |
|---|---|---|
| `npm test` | Smoke tests | Covers core / mcp / cli modules |
| `npm run check` | Build + contract consistency | Ensures code matches adapter contracts |
| `npm run eval` | Full hand-off gate | doctor + bootstrap + check + test |

`npm run eval` is the final delivery gate — all four stages must pass for the integration to be considered sound. For broader testing strategies, see the CI practices in [Ch.16](ch16).
