# 总体架构设计

## 四层架构一览

AIH 的架构分为四层加一个横切面，每层职责分明：

<figure>
<img src="assets/tutorial/arch-overview.svg" alt="AIH 四层架构图" />
<figcaption>图：AIH 四层架构 —— L0 接入层 → L1 内核层 → L2 规程层 → L3 技能层，横切面覆盖权限、审计与门禁</figcaption>
</figure>

```
L3 技能层   skills/            按需加载的领域知识，可由 skill-creator 自进化
L2 规程层   APP.md · harness.yml · scripts · tasks · docs/decisions.md
L1 内核层   core/              SessionLog · ToolRegistry(守卫管线) · AgentLoop(turn/step) · Seams(LLM/权限)
L0 接入层   mcp-server/        AppAdapter: Context(读) / Action(写,带权限) / Event(流)
横切面       权限三档 allow/ask/deny · 审计日志 · eval 交接门禁
```

- **L0 接入层**：一个应用 = 一个 `AppAdapter`（`descriptor` + `context(query)` + `actions`）。这是**唯一**的接入面。MCP / CLI / SDK 三种形态都复用同一 L0 契约（详见 [第 8 章「MCP 与接入形态」](ch08)）。
- **L1 内核层**（`core/`）：SessionLog、ToolRegistry、AgentLoop、Seams——内核不绑定任何业务，工具由 L0 注入。
- **L2 规程层**：`APP.md`（应用契约）、`harness.yml`（声明式配置）、`scripts/`（doctor/check/eval 门禁）、`docs/decisions.md`（决策记录）。
- **L3 技能层**：SKILL.md 三级加载（project > user > builtin）+ BM25 相关性自动建议 + 外部 registry 安装。
- **横切面**：权限三档（allow / ask / deny）含 pattern/路径作用域；审计日志逐条写入 `.aih/tool-audit.jsonl`；`npm run eval` 作为交接门禁。

## 核心数据流

一次用户交互经过以下路径：

```
用户输入
  → AgentLoop turn（L1）
    → ToolRegistry 接收工具调用请求
      → 权限守卫：allow / ask(deny) / deny
        → 钩子链（脱敏 / 计时 / 审计）
          → AppAdapter.action()（L0，执行实际业务操作）
            → AppAdapter.event()（可选，推送变更事件）
              → SessionLog.append()（写入 append-only JSONL）
                → 结果返回 AgentLoop → 下一步或输出给用户
```

关键设计原则：

- **append-only**：会话日志和审计日志只追加不修改，崩溃可恢复，回滚 = 前缀分叉。
- **判断与执行解耦**：Goal 裁判（独立 LLM 调用判断目标是否达成）和 best_of_n 裁判独立于执行代理。
- **并行只读**：单步内连续的只读工具调用并发执行（上限 `AIH_TOOL_CONCURRENCY`，默认 4），写类保持串行。

## Seam 可替换机制

Seam（接缝）是 AIH 架构中最重要的设计模式。`core/seams/` 定义了以下可替换接口：

| Seam | 作用 | 替换场景 |
|---|---|---|
| **LLM 适配器** | 把 LLM 调用抽象为统一接口 | 切换 DeepSeek / OpenAI / 本地模型 |
| **沙箱后端** | 工具执行的隔离环境 | local → bwrap → remote（D#12） |
| **审批门** | 决定 allow/ask/deny 路由 | 自定义审批流程 |
| **技能加载器** | 发现和加载 SKILL.md | 自定义技能发现策略 |

Seam 的核心价值是：**可插拔不锁死**。你可以替换 LLM 供应商而不改动一行内核代码；可以切换沙箱策略以适应不同部署环境。

## 分层配置体系

AIH 的配置分层堆叠，从应用到项目到用户逐层覆盖：

| 配置源 | 位置 | 作用 |
|---|---|---|
| `APP.md` | 项目根目录 | 应用智能体操作契约——唯一事实源，定义能力边界、接入原语、变更规则 |
| `harness.yml` | 项目根目录 | 声明式 harness 配置（LLM 参数、模型选择等） |
| `aih.json` | 项目根目录 | 运行时配置（provider、model、API key 等） |
| 项目信任门 | `cli/src/project-trust.ts` | 首次打开项目时的信任确认 |
| 环境变量 | `AIH_API_KEY` / `AIH_MODEL` / `AIH_BASE_URL` | 覆盖配置文件中的对应项 |

配置加载由 `cli/src/config.ts` 统一处理，优先级：环境变量 > CLI flags > `aih.json` > `harness.yml` > `APP.md` 默认值。

## 关键设计决策总结

| 原则 | 含义 |
|---|---|
| 通用内核 + 应用工具 | 内核不绑定任何业务，工具由 AppAdapter 注入 |
| append-only | 会话/审计只追加，回滚 = 前缀分叉，崩溃可恢复 |
| Seam 优先 | LLM/沙箱/审批/技能都是接缝，可插拔不锁死 |
| 判断与执行解耦 | Goal 裁判、best_of_n 裁判独立于执行代理 |

理解了这四层架构后，你就可以开始[动手实现自己的 AppAdapter](ch04)了——从一个最简单的 L0 适配器开始，逐步接入技能层和规程层。
