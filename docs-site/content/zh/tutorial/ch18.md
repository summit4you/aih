# 第18章 设计哲学与最佳实践

本章梳理 AIH 项目的核心设计哲学与日常使用建议，帮助开发者在真实项目中做出正确决策。

## 18.1 核心设计原则

AIH 围绕三条不可妥协的原则构建：

**追加只读（Append-only）**：会话和审计日志永远不会被原地修改。回滚 = 从某个前缀重新分叉出新会话。这让历史可追溯、可复现。

**缝优先（Seam-first）**：每一个可插拔点都是接口——LLM、沙箱、审批门控、技能加载器。新能力通过实现接口注入，而非修改内核。

**通用内核 + 注入应用工具**：AIH 内核不绑定任何具体应用逻辑。应用通过 `AppAdapter` 将工具注入 `ToolRegistry`，交给 `AgentLoop` 执行（详见 [第 17 章](ch17)）。

## 18.2 信任模型

AIH 的信任模型建立在明确边界之上（参见 [APP.md](../adapter)）：

- **本地单操作者**：信任边界 = 宿主机 OS 用户本身。
- **权限三态**：`allow`（免确认）、`ask`（需用户确认）、`deny`（硬拒绝）。写操作默认 `ask`。
- **凭证脱敏与所有者隔离**：敏感凭证在日志中被脱敏，不同应用的上下文互相隔离。
- **沙箱缝**：执行环境可通过沙箱接口隔离。
- **否定红线**：`deny` 权限不可被模型覆盖。

**不在威胁模型中的**：纯提示注入攻击（prompt-injection-only）。需要真正隔离时，应使用独立的 agent/host（独立 OS 用户或容器），而非依赖 prompt 或会话层面的隔离。

## 18.3 治理与演进准则

AIH 采用分层治理：

- **OC#2 核心逐调税（per-call tax）** vs **技能/扩展层**：同一功能有 ≥2 处调用时，提取为缝进入 core/SDK；一次性领域需求留在 skill/extension 层。
- **质量回归门控**：`aih quality --mock` 基于 FB#4 的 buffbench 风格任务套件 + 基线，实时运行时对回归零容忍。
- **覆盖率计分卡**：`aih coverage --profile release`（OC#6），覆盖率 ID + 证据模式，注册表由 smoke 分组自动派生、永不漂移。
- **eval 交付门禁**：`npm run eval`，详见 [第 17 章](ch17)。

## 18.4 最佳实践清单

| 实践 | 说明 |
|---|---|
| **先计划再构建（Tab）** | 高风险变更前用 plan-then-build 模式，AI 先输出方案再执行 |
| **写操作保持 ask** | 除非完全可控，否则不要将写操作设为 `allow` |
| **优先并行只读** | 多个读工具可并行调用，显著缩短交互延迟 |
| **会话保持追加只读** | 便于重放和调试，不要修改历史条目 |
| **设置 /goal 条件** | 长时间自主任务用 `/goal` 设定终止条件，防止无限循环 |
| **用技能承载领域知识** | 将领域知识放入 skill，而非塞进 system prompt |
| **保持扁平配置** | 顶层 `model` / `baseUrl` 为推荐形式；旧配置仍然合法，迁移时仅标记 `CONFIG_SCHEMA_VERSION`，不触碰扁平字段 |

## 18.5 总结与展望

AIH 的设计哲学可概括为：用最小内核、最强缝、最清晰信任边界，构建可演进的 AI agent 基础设施。掌握 [快速上手](../quickstart)、[配置细节](../config) 和 [第 17 章](ch17) 的实践流程后，你已经具备将任何应用接入 AIH 的能力。接下来，探索 skill 体系和社区生态将帮助你走得更远。
