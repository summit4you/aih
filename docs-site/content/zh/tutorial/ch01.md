# AI 编程助手时代与 AIH 的定位

## 从补全到智能体：编程助手的三次跃迁

第一代编程助手做的是**行内补全**——光标处弹出建议，Tab 接受。第二代引入了**对话式问答**——你描述需求，模型返回代码片段。今天我们正进入第三代：**智能体编码（agentic coding）**——模型拥有工具（读文件、跑命令、编辑代码），自主规划多步执行，像一个有权限边界的开发者一样工作。

AIH（App Intelligence Harness）正诞生于这个转折点。正如其 README 所述：

> 让任意普通应用（Web / 桌面 / 移动 / 后端服务）通过标准化接入获得 AI 能力的通用框架。

它不只是一个"编程助手"，而是一个**应用智能体接入框架**（App Intelligence Harness）。编程场景只是它最先落地的用例之一。

## AIH 的谱系：deepseek-harness + opencode

AIH 融合了两个上游项目的核心设计：

| 来源 | 核心借鉴 | 落点 |
|---|---|---|
| deepseek-harness | append-only Session Log、守卫式工具管线、Agent Loop、可替换接缝（Seam） | `core/`（L1 内核） |
| opencode | build/plan 双模式、权限模型、SKILL.md 渐进披露、TUI 交互 | `cli/`（CLI + TUI）、技能加载 |

**append-only 会话日志**意味着每条事件（工具调用、LLM 响应、用户输入）只追加不修改——崩溃可恢复、审计可回放。**守卫式工具管线**（ToolRegistry）在每次工具执行前经过权限检查（allow / ask / deny）和钩子链（脱敏、计时、审计）。**Seam（接缝）**则把 LLM 适配器、沙箱后端、审批门、技能加载器定义为可替换的接口——切换模型供应商或审批策略时无需改动内核。

## 三种接入形态

AIH 的核心价值是"不改业务代码"就接入智能体。它提供三种接入形态：**MCP 外挂**、**CLI 接入**和**内嵌 SDK**。三种形态共享同一个 **L0 契约**——`AppAdapter` = `descriptor`（应用描述）+ `context(query)`（读状态）+ `actions`（写操作，带权限）。

> 三种形态各自的入口、适用场景与详细对比，见 [第 8 章「MCP 与接入形态」](ch08)。这里只点到为止，不再重复展开。

## AppAdapter：一切的起点

接入 AIH 只需实现三个原语：

| 原语 | 类型 | 权限 | 说明 |
|---|---|---|---|
| **Context** | 读 | `allow`（直接执行） | 查询应用状态 |
| **Action** | 写 | `allow` / `ask` / `deny` | 执行业务操作 |
| **Event** | 流 | 可选 | 变更事件推送 |

以仓库内置的 todo-app 示例为例（`mcp-server/src/app-adapter.ts`），`list_todos` 是一个 `allow` 级 Action，`toggle_todo` 和 `remove_todo` 是 `ask` 级——执行前需用户确认。这个三档权限模型贯穿整个 AIH 架构。

## 为什么是"通用框架"

AIH 刻意**不绑定业务**。内核（`core/`）不包含任何业务逻辑；所有应用特定的工具由 `AppAdapter` 注入。这意味着同一个 AIH 内核可以驱动代码编辑器、数据库管理工具、CI 流水线、移动端调试面板——只要它们实现 L0 契约。这种设计让"给任意应用附加智能"成为可能，而不仅仅是"给程序员写一个更好的 Copilot"。

## 第一次使用：30 秒跑起来

初学阶段不必一开始就接真实的大模型。AIH 内置一个 todo 待办示例应用，配合 `--mock` 离线模式，**不需要 API Key**，就能体验“指挥智能体做事”的完整链路。跟着做一遍：

```sh
npm run bootstrap && npm run check   # 第一次：装依赖 + 构建
npm run cli -- run "加一条待办：买牛奶" --mock
```

你能看到它真的**一路做下去**：

```text
[aih-mcp-server] serving app "todo-app" over stdio
[session: new .aih/sessions/...jsonl]
⚙ add_todo {"text":"from aih cli"}
Added via mock.
[turn ..., 2 step(s), end_turn]
```

这一小段已经涵盖了整条链路：**CLI → MCP 服务器 → todo 应用的工具 → 守卫执行 → 会话日志落盘**。也就是说，`--mock` 验证的是“管道本身通不通”，但它**不产生真正的智能思考**——模型回答是内定的演示值。想要真正的推理，需要配置一个模型供应商（见 [第 7 章「Provider 多模型适配层」](ch07) 和 [配置](../config)）。

我们也可以像菜鸟教程那样，建一个极小的文件让 AI 解释：

```sh
printf 'function add(a, b) { return a + b; }\nconsole.log(add(2, 3));\n' > hello.js
npm run cli -- run "解释 hello.js 这个文件在做什么，用新手能理解的方式说明" --mock
```

配好真实模型后，把 `--mock` 换成一次真实的 `aih run`，AI 就会真正读懂文件、给出解释、甚至动手修改。对于“命令行怎么拼”这类问题，菜鸟教程式的手把手示范最有效；而**每个命令背后到底做了什么**、为什么安全，正是本书后续章节要深挖的。
